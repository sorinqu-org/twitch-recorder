# Конфигурация

Все настройки читаются из одного YAML-файла (`--config`, по умолчанию `config.yaml`
в текущем каталоге). Значения переменных окружения вида `$VAR` разворачиваются
рекурсивно во всех строковых, списковых и словарных значениях (`expand_env`).

Значения по умолчанию ниже взяты из `Settings.load` в `twitch_recorder.py` -
если код и документация где-то расходятся, прав код.

## Секция `twitch`

| Ключ | Тип | Значение по умолчанию | Что делает | Когда менять |
| --- | --- | --- | --- | --- |
| `twitch.credentials_file` | строка (путь) | `""` (не задан) | Если указан, сервис читает из этого файла секцию `twitch` и объединяет её с той, что задана прямо в `config.yaml` (ключи из `config.yaml` перекрывают файл секретов, кроме самого `credentials_file`). Позволяет держать `config.yaml` в репозитории/бэкапе, а секреты - отдельно с правами `600`. | Почти всегда: так секреты не попадают в общий конфиг. |
| `twitch.client_id` | строка | `""` | Client ID Twitch-приложения (client credentials grant). Обязателен. | При смене/ротации Twitch-приложения. |
| `twitch.client_secret` | строка | `""` | Client secret того же приложения. Обязателен. | При ротации секрета. |
| `twitch.oauth_token` | строка | `""` | Опциональный OAuth-токен, передаётся в `streamlink` как `Authorization: OAuth ...` (префикс `oauth:` из значения обрезается автоматически). Нужен только для приватных/подписных стримов. | Если `streamlink` без токена не может открыть поток. |

`client_id`/`client_secret` не должны содержать `$` после разворачивания переменных
окружения - если содержат, значит переменная окружения не была задана, и `Settings.load`
поднимет ошибку.

## Верхний уровень

| Ключ | Тип | Значение по умолчанию | Что делает | Когда менять |
| --- | --- | --- | --- | --- |
| `channels` | список строк | `[]` | Twitch login-имена каналов для мониторинга. Приводятся к нижнему регистру, дубликаты убираются. Хотя бы один канал обязателен. | При добавлении/удалении стримера. |
| `download_directory` | строка (путь) | `./downloads` | Корень, куда пишутся чанки: `download_directory/<channel>/<started_at>/chunk_N.mp4`. Путь разворачивается (`~`, переменные) и приводится к абсолютному. | Обычно один раз при установке. |
| `check_interval` | целое, секунды | `60` (минимум **15**, принудительно) | Как часто опрашивать Twitch Helix `GET /streams`. | Увеличить, если упираетесь в rate limit Helix при большом числе каналов. |
| `chunk_duration` | целое, секунды | `3600` (минимум **60**, принудительно) | Длина одного `chunk_N.mp4`, передаётся в `ffmpeg -segment_time`. | Если процессору/аплоаду нужны более мелкие или крупные файлы. |
| `quality` | строка | `best` | Селектор качества, передаётся в `streamlink` как позиционный аргумент. | Обычно не трогают. |
| `max_quality` | строка | `1080p` | Верхняя граница качества: передаётся в `streamlink --stream-sorting-excludes >VALUE`, то есть исключает всё, что выше указанного. **Важно**: см. раздел "Расхождение по качеству" ниже. | Поднять, если каналу нужно 1440p/4K и полоса/место позволяют. |

## Секция `rclone`

Нужна только если чанки заливаются напрямую на облачный remote (без `processor.command`
или в дополнение к нему для остальных каналов - но в текущей версии выбор идёт на
уровне всего сервиса: если `processor.command` задан, используется он, `rclone`
не вызывается вообще, см. `UploadManager._worker`).

| Ключ | Тип | Значение по умолчанию | Что делает | Когда менять |
| --- | --- | --- | --- | --- |
| `rclone.remote` | строка | `""` | Имя rclone remote (без завершающего `:`). Обязателен, если не задан `processor.command`. | При смене облачного хранилища. |
| `rclone.base_path` | строка | `Twitch` | Префикс пути на remote, слэши по краям обрезаются. Итоговый путь: `remote:base_path/channel/started_at/chunk_N.mp4`. | Если нужна другая структура на диске. |
| `rclone.config` | строка (путь) | `""` (используется конфиг rclone по умолчанию) | Явный путь к `rclone.conf`, передаётся как `rclone ... --config PATH`. | Когда rclone настроен не в домашнем каталоге сервисного пользователя. |
| `rclone.delete_after_upload` | булево | `false` | Удалять локальный чанк после успешной загрузки/обработки. | Включать только если есть отдельное хранение оригиналов (например, сам процессор их архивирует). |
| `rclone.workers` | целое | `2` (минимум **1**, принудительно) | Число фоновых потоков `UploadManager`, разбирающих очередь чанков. | Увеличить при большом числе одновременных каналов/чанков. |

## Секция `processor`

Альтернатива `rclone`: каждый готовый чанк передаётся внешней команде. Именно так
`twitch-recorder` интегрируется со StreamSlice (см. README.md и docs/DEPLOYMENT.md).

| Ключ | Тип | Значение по умолчанию | Что делает | Когда менять |
| --- | --- | --- | --- | --- |
| `processor.command` | список строк | `[]` | Базовая команда без `--input`; сервис сам дописывает `--input <chunk.mp4>` в конец и запускает через `subprocess.run`. Обязателен, если не задан `rclone.remote`. | При смене пути до интерпретатора/скрипта процессора. |
| `processor.max_attempts` | целое | `8` (минимум **1**, принудительно) | Сколько раз пытаться обработать один чанк, включая первую попытку, прежде чем считать его окончательно неудачным. | Увеличить для более устойчивых, но медленных пайплайнов. |
| `processor.retry_initial_seconds` | целое, секунды | `60` (минимум **1**) | Задержка перед первым повтором. Далее растёт экспоненциально: `initial * 2^(attempt-1)`, ограничено сверху `retry_max_seconds`. | Уменьшить для быстрых временных сбоев, увеличить - для дорогих внешних сервисов. |
| `processor.retry_max_seconds` | целое, секунды | `1800` (минимум **1**) | Верхняя граница задержки между повторами. | Ограничить максимальное время простоя между попытками. |
| `processor.timeout_seconds` | целое, секунды | `18000` (минимум **60**) | Таймаут одного вызова процессора (`subprocess.run(..., timeout=...)`). Истечение таймаута приводит к исключению `subprocess.TimeoutExpired`, что тоже уходит в retry. | Подбирать по реальному времени обработки самого длинного чанка. |

## Ретраи и что происходит после исчерпания попыток

- Каждый неуспешный вызов процессора (ненулевой код возврата **или** исключение при
  запуске) увеличивает счётчик попыток для чанка и планирует повтор через
  `threading.Timer` с задержкой `min(retry_initial_seconds * 2^(N-1), retry_max_seconds)`.
- При прямой загрузке через `rclone` (без `processor.command`) логика проще: при
  неуспехе сервис ждёт фиксированные 30 секунд и кладёт чанк обратно в очередь -
  отдельного счётчика попыток и предела в этом режиме нет.
- Как только число попыток процессора достигает `processor.max_attempts`, сервис
  вызывает `LOG.critical(...)` и **оставляет файл на диске навсегда**. Он не
  удаляется, не переносится в отдельную папку и не будет автоматически повторён
  снова - при следующем перезапуске сервиса он не попадёт в очередь заново
  (проверяется по множеству `failed`, которое живёт только в памяти процесса, но
  файл также не входит и в `.uploaded.json`). На практике это означает: если чанк
  окончательно "провалился", **разбирать такие файлы нужно руками**, ориентируясь
  по записи `LOG.critical` в журнале.
- Отдельно от ретраев процессора есть карантин повреждённых MP4: если `ffprobe`
  трижды (`INVALID_QUARANTINE_THRESHOLD = 3`) подряd не может подтвердить, что файл -
  валидный MP4 с положительной длительностью, чанк также помечается как
  окончательно неудачный (`LOG.critical`) и больше не подхватывается сканированием
  каталога.

## Расхождение с README на хосте: качество ограничено не 1080p

Устаревший README на боевом хосте утверждает "качество ограничено 1080p", но
боевой `config.yaml` содержит `max_quality: 1440p60`. Реального ограничения "1080p"
в коде никогда не было - `max_quality` полностью настраиваемый ключ, значение по
умолчанию в коде `1080p`, но конкретная инсталляция может (и уже делает) поднять
его выше. Документация была не синхронизирована с конфигом. В этом репозитории
пример (`config.example.yaml`) использует `1080p60` как безопасный дефолт, а
фактический потолок качества для вашей записи всегда определяется значением
`max_quality` в вашем `config.yaml`.

## Лишние ключи в боевом `twitch-credentials.yaml`

Боевой файл секретов на хосте содержал ключи `channels`, `download_directory`,
`check_interval`, `chunk_duration`, `gemini.model` - видимо, скопированные туда по
ошибке из `config.yaml` или из конфигурации StreamSlice. `Settings.load` при
разборе `credentials_file` берёт из него **только** секцию `twitch`
(`credentials.get("twitch", credentials)`), всё остальное молча игнорируется - это
не баг, но и не документированное поведение, на которое стоит рассчитывать.
`credentials.example.yaml` в этом репозитории содержит только то, что реально
используется: `twitch.client_id`, `twitch.client_secret`, `twitch.oauth_token`.
